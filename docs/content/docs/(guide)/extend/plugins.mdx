A plugin adds things to a host. Each thing is a **feature**: packages, set-up steps, a guide for the agents working there, and actions on the host. A plugin can have several features, each switched on by itself. Coding agents come as plugins too, [installed](#installing-a-plugin) like any other. A plugin can also bring a [provisioner](/docs/deploy/provisioners) that creates machines.

## Plugins that come with Rookery

| Plugin | Features | Adds |
| --- | --- | --- |
| `github` | `github/cli` | `gh`, its sign-in, and git set up to use its login |
| `unity` | `unity/cli`, `unity/editor` | The Unity CLI and an editor, with sign-in, license activation and status |
| `backup` | `backup/restic` | Nightly restic snapshots ([Backups](/docs/use/backups)) |
| `docker` | `docker/engine` | A Docker engine on a node, and provisioners for containers and Compose projects ([Provisioners](/docs/deploy/provisioners)) |
| `incus` | `incus/server` | An Incus server on a node, and provisioners for VMs and containers ([Nodes](/docs/use/nodes)) |

They are the packages of a Hatchery registry named `rookery`, in the `plugins/` folder of the provisioning source, such as `rookery/github`. Rookery installs them through Hatchery like any other plugin, so `eggs.lock` lists them with their versions. The registry is part of the release, the container image, the USB installer and the cloud seed, and Rookery reads it with no network. When Rookery starts, it installs what the registry has and the install folder lacks, and puts each of these plugins at the registry's version. A newer Rookery brings their newer versions.

A host gets the features listed in `rookery_plugin_features`. Unless that is set, it lists `github/cli`.

## Switching features on

Features are off until chosen. The set-up lists them in their groups next to the built-in entries, and `rookery host set HOST feature.PLUGIN/FEATURE=on` switches one after the fact. The choice is stored in the profile:

```json title="In studio's profile"
{ "ansible_vars": { "rookery_plugin_features": ["unity/cli", "unity/editor"] } }
```

and reaches a running host with **Apply this configuration**.

## Installing a plugin

A plugin is a [Hatchery](https://aiviarium.github.io/hatchery/) package with a `rookery` target. Rookery installs it with the Hatchery library, from the plugin registries you give it.

| Location | For |
| --- | --- |
| `plugins/` in the provisioning source | The registry of the plugins that come with Rookery |
| `~/.config/rookery/plugins/GROUP/ID/` | Every installed plugin, with Hatchery's `eggs.lock` in `~/.config/rookery/plugins/` |
| `~/.config/rookery/hatchery.kdl` | The plugin registries |

Rookery changes that folder itself, and a package copied into it by hand is not read. Use `rookery plugin add` and `rookery plugin remove`.

### Plugin registries

A registry is a git repository, a static registry over HTTPS, or a folder. Rookery searches the [registry named `rookery`](#the-registry-named-rookery) first, then the others in the order they were added.

```bash
rookery plugin registry add git https://github.com/example/rookery-plugins.git
rookery plugin registry add http https://eggs.example.org --key ed25519:… --min-age 7d
rookery plugin registry add dir /srv/eggs --only example
rookery plugin registry list
rookery plugin registry remove https://eggs.example.org
```

| Option | Meaning |
| --- | --- |
| `--only GROUP` | The registry serves only the packages of this group. Repeat it for more |
| `--key ed25519:…` | Eggs from it must be signed with this key |
| `--unsigned-tags` | With `--key`: a version of a git registry that has only a tag is installed from source anyway |
| `--min-age 3d` | How long a new version waits before it is installed. `0` installs it at once |

A new version from a registry read over the network waits 3 days by default before it is installed. A version from a git tag counts from when Rookery first saw it. Versions from a `dir` registry or a `git` registry at a folder don't wait. `--allow-young` on `rookery plugin add` installs a version that is still waiting. The file the registries are in is described in [Hatchery's documentation](https://github.com/aiviarium/hatchery/blob/main/docs/hatchery-kdl.md).

### The registry named rookery

The registry in the provisioning source is there without a line in `hatchery.kdl`. `rookery plugin registry list` shows it as `built in`. It serves only the group `rookery`, and a new version from it is installed at once. A line with `name=rookery` takes its place, and `off rookery` turns it off. Other registries go beside it:

```kdl title="~/.config/rookery/hatchery.kdl"
registries {
  git "https://github.com/example/rookery-plugins.git" name=rookery
  http "https://eggs.example.org"
}
```

```bash
rookery plugin registry add git https://github.com/example/rookery-plugins.git --name rookery
rookery plugin registry disable rookery
rookery plugin registry remove rookery        # its line goes, and the one in the source is back
```

| `hatchery.kdl` | The registry named `rookery` |
| --- | --- |
| No file, or no line named `rookery` | The one in the provisioning source, searched first |
| `KIND "LOCATION" name=rookery` | That registry, where its line is. It serves only the group `rookery` unless the line has `only` |
| `off rookery` | None |

The plugins this registry installed come with Rookery, and stay while it's on. After a line takes its place, `rookery plugin update` installs them from that registry. With it off, they stay installed as plugins of a registry that is gone, and `rookery plugin remove` removes them. Removing the line brings back the registry in the source, and Rookery installs what it has.

### Adding and removing

`rookery plugin list` lists every plugin with its features. `rookery plugin show NAME` says what one brings.

```bash
rookery plugin add example/hello              # the newest version the registries allow
rookery plugin add example/hello@^1.2         # the newest within a range
rookery plugin add hello                      # the first registry that has an id hello
rookery plugin add https://eggs.example.org/hello-1.2.0.egg
rookery plugin add --git https://github.com/example/hello.git --ref v1.2.0
rookery plugin add ./hello                    # a package folder, packed into an egg
rookery plugin add ./hello-1.2.0.egg          # an egg that hatchery pack made
rookery plugin list                           # what is found, and from where
rookery plugin remove hello                   # by its id, or as example/hello
```

`--git` installs one folder of a git repository, which `--path` names. `--ref` is a tag, a branch or a commit. Without it, Rookery takes the default branch. `--allow-young` installs a version that is still inside its registry's minimum release age.

Hatchery checks each package before it installs it. A package is refused when its `package.kdl` doesn't say which Rookery versions it works with, or gives others, and so is one whose `plugin.json` breaks the [plugin contract](/docs/extend/writing-plugins#checking-a-plugin). Installing runs none of the plugin's code. Its Ansible tasks run when a host is applied.

After each change, Rookery writes `hatchery.kdl`, `eggs.lock`, `.hatchery/seen.toml` with when each version was first seen, and the eggs that were sent, to its [store](/docs/use/store). A machine restored from the store gets them back and installs what `eggs.lock` lists, from the same registries.

### Updating a plugin

```bash
rookery plugin update --check                 # which have a newer version
rookery plugin update hello                   # one, by its id or package
rookery plugin update                         # all of them
```

`--check` asks the registries. A newer version that waits for its minimum release age, was withdrawn or cannot be installed here is named with the reason. `update` installs the newest allowed version and then lists the hosts that are behind. `rookery plugin update --check` says which have a newer version, as `update available: 1.0.0 → 1.1.0`.

| Came from | Updated by |
| --- | --- |
| A registry | `rookery plugin update` |
| A folder of a git repository | `rookery plugin update`, which takes the newest commit of its branch. One at a tag is added again with the new tag |
| An egg, by its address or sent | Adding the new one, which replaces it |
| The registry named `rookery` | A newer Rookery, by `rookery update` or a newer server image, which installs their new versions when it starts |

A host keeps what it was applied with until it is applied again. After an update, `rookery rollout` applies the hosts that are behind ([Updates](/docs/use/updates#bringing-hosts-up-to-date)).

### On a Rookery server

With a [Rookery server](/docs/use/server) set, `rookery plugin` and `rookery plugin registry` show and change the server's plugins and registries, which needs an admin of the server. The server installs packages from its own registries and fetches `https://` addresses itself. It never installs a path of its own machine. `rookery plugin add` packs a folder on your machine into an egg and sends it, or sends an egg file as it is. A `dir` registry, or a `git` registry at a folder, is read with the server's rights, so only a caller on the server's own socket adds one.

The server's hosts can have a new plugin's features as soon as it is installed. Its Ansible tasks run on the server when a host is applied, so installing is part of set-up.

A plugin of yours with the same id as one that comes with Rookery replaces it.

### The methods

`rookery plugin` and `rookery plugin registry` call these methods. A shell and a script use them too.

| Method | Does |
| --- | --- |
| `plugins.list` | The plugins installed with their manifests, their state and the addresses of their client halves. What a shell loads |
| `plugins.add` | Installs a package of the registries, an `https` egg, or one folder of a git repository, with `spec`, `git`, `path`, `ref` and `allowYoung` |
| `plugins.upload` | Installs a plugin from an egg the caller sends, in base64. What `rookery plugin add` uses for a folder or a file of your machine |
| `plugins.check` | Asks the registries for a newer version of each plugin, which is `rookery plugin update --check` |
| `plugins.update` | Updates one plugin, or all of them, to the newest version its registry offers |
| `plugins.remove` | Removes a plugin, by its id or its package. Its host half stops first |
| `plugins.registry.list`, `add`, `remove` | The registries, in search order, with their keys |
| `plugins.reload` | Reads the plugin folder again, as after a change made beside the server |
| `plugins.activate` | Starts a plugin's host half, as using what it contributes does |
| `plugins.rpc` | Calls a method a plugin's host half registered ([Host halves](/docs/extend/writing-plugins#host-halves)) |

Installing, updating, removing and the registries need an admin. `plugins.list` and `plugins.activate` are open to anyone signed in.

## The extension host

A plugin's host half runs on the server, in a Bun process of its own. Rookery starts the extension host's entry, `host/dist/main.js` of its provisioning source unless `ROOKERY_EXTHOST` names another, with the Bun program of `ROOKERY_BUN`. The host half runs in a worker of that process, and the process talks JSON-RPC 2.0 with the server over its standard input and output, one message a line.

The pipes are the plugin's identity. A process speaks for its plugin alone, and what it says of another plugin is ignored.

A host half gets none of the server's environment but `PATH`, `HOME`, `LANG`, `LC_ALL` and `TZ`, with `NODE_PATH` for the extension host's own packages and `ROOKERY_EXTHOST_PROTOCOL`. It does not get the database's address or the server's key. The server and each host make themselves non-dumpable, which keeps one host from opening another's pipes, or reading another's or the server's memory and environment through `/proc`.

That is a mitigation, not a sandbox. Every host half runs as the server's own user and can read the files that user can, such as the secret key file and the configuration folder. A host half is code an admin installs and trusts: install plugins whose source you trust, as you would any program on the server.

A host half that ends, that does not stop a call past its deadline, or whose process holds more memory than `ROOKERY_EXTHOST_MEMORY_MB` (512 MiB unless set) counts as a crash. The memory is read every two seconds. After five crashes in a minute the plugin is failed, and an admin starts it again, also as a dependency of another plugin.

## Client halves and the shell

A plugin may have a client half: a built module that a shell loads in the browser. `client` in `plugin.json` names its entry, and `styles` a stylesheet loaded with it. Both are paths in the plugin's `rookery/` folder.

The files are served at `/plugins/{id}/{hash}/{path}`, where `hash` is the SHA-256 of the client half's files. A browser keeps a version for good, and a new version has an address of its own. An address with another hash answers `404`. The route needs no sign-in, as a page loads a shell before anyone signs in: put nothing secret in a client half.

`plugins.list` gives each plugin's `client.script` and `client.styles`, which a shell loads. The same answer carries the plugin's `manifest` and its state, and a plugin that failed carries why in `problem`. The server tells every signed-in connection `plugins.changed` when a plugin is installed, updated or removed. A shell reads the plugin again from `plugin`, or drops it when that is null.

A shell is a plugin whose `plugin.json` has `contributes.shell.entry`, the built page. The entry is in a folder of the plugin's target, as the rest of the shell's files are served beside it. One plugin on a server is the shell, and `/` serves its files, with its entry for any path that names no file, so that the shell's own routes load it. `ROOKERY_SHELL_DIR` serves a built shell from a folder instead. Without either, `/` is a page that says that no shell is installed.

## Connection types

A plugin that talks to an outside service declares its `contributes.connectionTypes`. `fields` is a JSON Schema of the object a connection keeps, `title` and `description` label the form a shell builds, and `scopes` says which of `global`, `space` and `user` the type takes. `test` asks the host half to answer whether a connection works.

`secret` names the one field whose value is a secret, or is absent. The server seals it apart from the connection's config as its credential, and answers the config without it. Only the plugin that declares the type reads the credential, through `connections.resolve`. No other plugin does, and Rookery's own `registry` and `http` types are for people and the shell alone. A type whose `secret` is anything but a list of no names or one name is refused. A secret never stays in the plain config.

## Server events

The server publishes events under its own plugin id, `rookery/NAME`:

| Event | Payload | When |
| --- | --- | --- |
| `rookery/hosts.changed` | `host`, `info`, `change`, `from`, `removed` | A host is `added`, `changed`, `renamed` or `removed`. `info` is the host as `hosts.get` gives it |
| `rookery/resources.changed` | `resource`, `provisioner`, `kind`, `change` | A resource is `created`, `changed` or `removed` |
| `rookery/jobs.changed` | `job` | A job's state, progress or outcome changed |

A client half subscribes with its plugin's own API, and takes a full name for an event of the server:

```ts
const off = await rookery.events.subscribe("rookery/hosts.changed", (payload) => {
  // payload is { host, info, change, from, removed }
})
```

A name without a `/` is the plugin's own, so `rookery.events.subscribe("hosts.changed", …)` in the plugin `hello` subscribes to `hello/hosts.changed`. A name with a `/` is taken as it is. Events are at most once: a connection too slow for a burst loses what does not fit, and `onDropped` says how many. A shell then reads again what it shows.

A host's channel message, a notification and a plugin's own events are separate from these: `topics.*` keeps a channel's messages, `notify.*` is a person's inbox, and `events.*` is at most once ([`rookery serve`](/docs/extend/serve#jobs)).

## Other install methods

| Method | Plugins |
| --- | --- |
| USB installer, cloud seed | The release archive contains the registry of the plugins that come with Rookery, and the installed plugins when built through Rookery |
| Container | Set `PLUGIN_FEATURES='["unity/cli"]'` for the build. Only the plugins that come with Rookery are in the build context |
| Plain Ansible | Pass `rookery_plugin_features`, and for plugins other than those in the source's `plugins/rookery/`, `rookery_plugin_dirs` with the folder of each one's `rookery` target (`{"ID": "/path/to/ID/rookery"}`). `rookery_plugin_labels` (`{"ID": "Name"}`) names the group of its actions, which is otherwise the id |

To write your own, see [Writing a plugin](/docs/extend/writing-plugins).
