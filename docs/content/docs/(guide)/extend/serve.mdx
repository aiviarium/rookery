`rookery serve` is Rookery's server. It keeps the hosts with their profiles, keys, secrets and jobs in a PostgreSQL database, and holds a link to each host's rookeryd. Crow, the `rookery` command line and scripts all use its one API of methods. Every method is in the [API reference](/docs/api/server).

```bash
export ROOKERY_DATABASE_URL=postgres://rookery:PASSWORD@db.example.org/rookery
export ROOKERY_SECRET_KEY_FILE=/etc/rookery/secret.key
rookery serve
```

It migrates the database, then serves. Several can run on one database: one leads and holds the links to the hosts and runs the jobs, the others stand by and take over when it stops. `/healthz` answers `200` on the leader and `503` on one standing by.

## Its settings

The server takes its settings from the environment:

| Variable | Means |
| --- | --- |
| `ROOKERY_DATABASE_URL` | The PostgreSQL database. Required |
| `ROOKERY_DATABASE_LOCK_URL` | A direct connection for the leader's lock, when `ROOKERY_DATABASE_URL` goes through a pooler |
| `ROOKERY_SECRET_KEY_FILE`, `ROOKERY_SECRET_KEY` | The key that seals secrets and the key ring in the database: 64 hex digits, or 32 bytes in base64. Without it the server runs and refuses what is sealed |
| `ROOKERY_LISTEN` | Where it listens, `127.0.0.1:7777` unless set. An address other machines reach also needs `ROOKERY_ALLOW_PUBLIC=1` |
| `ROOKERY_PUBLIC_URL` | The address people reach it at, such as `https://rookery.example.ts.net`. Sign-in links name it |
| `ROOKERY_SOCKET` | The unix socket of the command line on this machine, `server.sock` in Rookery's runtime folder unless set |
| `ROOKERY_ADMINS` | Accounts that are admins, apart by commas |
| `ROOKERY_OIDC_ISSUER`, `ROOKERY_OIDC_CLIENT_ID`, `ROOKERY_OIDC_CLIENT_SECRET_FILE` | Sign-in with an OpenID Connect provider instead of local accounts |
| `ROOKERY_SHELL_DIR` | A built shell, such as Crow's, served at `/` |

The server writes the files the hosts need, such as its key ring and the hosts' known keys, into Rookery's configuration and data folders on the machine it leads on.

## What it serves

| Methods | For |
| --- | --- |
| [`hosts.*`](/docs/api/server/hosts) | The hosts with their profiles, whether each answers and is behind, and the [actions](#actions) of each. A host's services, units, logs, processes and messages are methods of the host too |
| [`terminals.*`](/docs/api/server/terminals), [`env.*`](/docs/api/server/env) | Commands and terminals on a host, its files, and TCP connections to its ports |
| [`jobs.*`](/docs/api/server/jobs) | The jobs, one for each run of an action, with their log. `jobs.follow` streams it |
| [`keys.*`](/docs/api/server/keys) | The key ring Rookery logs in to hosts with |
| [`installation.*`](/docs/api/server/installation), [`registries.*`](/docs/api/server/registries) | The installation's actions, such as `rollout`, its secrets and settings, and the registries |
| [`provisioners.*`](/docs/api/server/provisioners), [`resources.*`](/docs/api/server/resources) | What makes machines and deployments, and what it made. Creating, changing and removing a resource are jobs |
| [`setup.*`](/docs/api/server/setup), [`plugins.*`](/docs/api/server/plugins) | What a new host starts from, and the server's plugins |
| [`auth.*`](/docs/api/server/auth), [`admin.*`](/docs/api/server/admin), [`access.*`](/docs/api/server/access) | Sign-in, accounts, tokens, and grants on hosts |
| [`topics.*`](/docs/api/server/topics), [`notify.*`](/docs/api/server/notify), [`storage.*`](/docs/api/server/storage), [`events.*`](/docs/api/server/events) | What the hosts publish on their channels, notifications, small values with revisions, and one stream of what changes |

## Actions

What Rookery does to a host or to the installation is an *action*. `hosts.actions` lists a host's, and `installation.actions` those of the installation. A host's controller has actions of its own, which are among the host's. A form can be built from an action's description. It has the arguments with their defaults and choices, a question to confirm, the level it needs, and whether it can run now.

| Action | Of | Runs | Answers |
| --- | --- | --- | --- |
| An action of the host's controller, such as `status` | The host | On the host, as a session | A job that copies its output. One that needs a terminal gives the session alone, to attach to |
| `apply` | The host | Here, as a job | A job |
| `install-controller` | The host | Here, as a job | A job. It installs rookeryd and box alone on an `ssh` or `managed` host |
| `seed` | The host | Here, at once | The seed's `user_data`, at once |
| `secrets` | The host | On the host, with the server's secrets | A job that follows the session |
| `rename` | The host | Here, as a job | A job. It gives the host the name in its `name` argument, with what the server keeps of it ([Renaming a host](/docs/use/moving#renaming-a-host)) |
| `upgrade-server` | A node with a Rookery server's container | On the node, as a session | A job that follows the session. It runs the server from the image of `version`, this server's own unless given ([The Rookery server on a node](/docs/use/nodes#the-rookery-server-on-a-node)) |
| `rollout` | The installation | Here, as a job | A job; its report says how each host went |

An action that the host's type rules out is listed with `available` false, and its `why` says which action changes the type.

`hosts.act` and `installation.act` run one, with its arguments and an optional `token`:

```json
{ "jsonrpc": "2.0", "id": 1, "method": "installation.act",
  "params": { "action": "rollout", "arguments": { "update": "yes" }, "token": "nightly-2026-11-13" } }
```

The same token again for the same action answers with the job the first call started, and nothing runs a second time. That lets a caller that lost the answer ask again. While an action changes a host, a second one that changes it is refused with `CONFLICT` until the first has ended, and so is a second roll-out. A job is followed with `jobs.get` and the `jobs.follow` stream, and `jobs.cancel` stops it. A job's log is kept with the job for `retention_days` (90 by default).

## Where it listens

The server serves `/ws`, `/rpc`, the sign-in pages under `/auth` and `/healthz` at `ROOKERY_LISTEN`. Every request there needs a browser's session or an access token, except sign-in itself.

On its own machine it also serves a unix socket, readable by its user only. The command line on that machine uses it, and its caller is an admin:

```bash
rookery server setup-key                 # a sign-in link for the first admin
rookery server token --user ada --admin  # an access token of ada, who is made an admin
```

<Callout type="warn" title="Plain HTTP">
  The server speaks plain HTTP. Serve it behind a TLS proxy such as Tailscale Serve or Caddy, or keep it on a private network such as your tailnet.
</Callout>

## Who gets in

People sign in with an account of the server, or with an OpenID Connect provider when `ROOKERY_OIDC_ISSUER` is set. The first admin signs in with the link `rookery server setup-key` prints. An admin then invites others with `auth.createLink`.

A host belongs to the account that added it. Its owner and the admins hold `manage` on it, and `access.grant` gives another account or a group `view`, `use` or `manage` on `env://NAME`:

| Level | May |
| --- | --- |
| `view` | See the host, its state, jobs and output |
| `use` | Open terminals, files and ports on it |
| `manage` | Change its profile, apply it, rename it, and run its actions and its controller's |

Each action says the role it needs, which `hosts.act` checks: `operate` is `manage` on the host, and `admin` an admin of the server, as removing a host's machine, a roll-out or a new key for Rookery need. Keys, secrets, registries, settings, provisioners and plugins need an admin.

Scripts and other programs use an access token: `auth.createToken` makes one for oneself, and `rookery server token` on the server's machine one for any account. It goes in `Authorization: Bearer`, or to the command line as `ROOKERY_TOKEN`, `--token-file` or `--token-stdin`. `rookery login URL` keeps it, or signs in through the browser.

## In a container

The `ghcr.io/aiviarium/rookery` image runs `rookery serve` at port 7777, as user `rookery` (uid 1000). Without `ROOKERY_DATABASE_URL` it runs a PostgreSQL of its own in `/data`, reached on a socket inside the container alone, and makes its secret key in `/config` the first time:

```bash
docker run -d --name rookery -p 127.0.0.1:7777:7777 \
  -e ROOKERY_PUBLIC_URL=http://127.0.0.1:7777 \
  -v rookery-config:/config -v rookery-data:/data \
  -v ~/.ssh:/home/rookery/.ssh:ro \
  ghcr.io/aiviarium/rookery
docker exec rookery rookery server setup-key
```

| Path | Holds |
| --- | --- |
| `/config/rookery/` | `secret.key`, and the folder of the server's own plugins |
| `/data/rookery/` | The database in `postgres/`, the server's SSH keys and known hosts, written from the database, and builds |
| `/home/rookery/.ssh` | Further SSH keys and configuration for reaching hosts |

A container that ran an older Rookery, with its store in `/data/rookery/rookery.db` or in `ROOKERY_STORE`, brings that store into the database the first time the new image starts ([The database](/docs/use/store#from-an-older-store)).

The image contains ansible-core, the OpenSSH client and Python, so it can also apply configurations, and git for installing plugins. See [A Rookery server](/docs/use/server) for using it from Rookery on another machine.
