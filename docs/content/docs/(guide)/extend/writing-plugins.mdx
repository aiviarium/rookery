A plugin is a [Hatchery](https://aiviarium.github.io/hatchery/) package with a `rookery` target. The package is a folder with a `package.kdl`. The plugin's files are in its `rookery/` folder, and `rookery/plugin.json` says what the plugin is and what it contributes, such as its host features and provisioners. Plugins are shared through plugin registries, such as a git repository of packages ([Installing a plugin](/docs/extend/plugins#installing-a-plugin)). The Unity plugin in `plugins/rookery/unity/` is a good one to copy.

## A minimal plugin

<Files>
  <Folder name="hello" defaultOpen>
    <File name="package.kdl" />

```kdl title="hello/package.kdl"
format 1

package {
  group example
  id hello
  version "1.0.0"
}

about {
  name "Hello"
}

targets {
  rookery {
    requires {
      rookery ">=0.6"
    }
  }
}
```

```json title="hello/rookery/plugin.json"
{
  "apiVersion": "1",
  "name": "Hello",
  "contributes": {
    "hostFeatures": [
      {
        "id": "cowsay",
        "group": "Development Tools",
        "label": "cowsay",
        "description": "Installs cowsay and adds a greeting to the host.",
        "summary": "`cowsay` is installed.",
        "packages": [
          "cowsay"
        ],
        "commands": [
          "cowsay"
        ],
        "actions": [
          {
            "name": "greet",
            "label": "Say hello",
            "run": "cowsay hello from $(hostname)"
          }
        ]
      }
    ]
  }
}
```

Install it with `rookery plugin add ./hello`, switch it on with `rookery host set studio feature/hello/greeting=on`, and apply the configuration. **Say hello** appears among the host's actions.

```kdl title="package.kdl"
format 1

package {
  group aiviarium
  id unity
  version "0.1.0"
}

about {
  name "Unity"
  summary "Unity CLI and editor for rookery machines."
  license MIT
  license Apache-2.0
  repository "https://github.com/aiviarium/rookery"
  keywords rookery-plugin
}

targets {
  rookery {
    requires {
      rookery ">=0.6"
    }
  }
}
```

| Node | Meaning |
| --- | --- |
| `package` | The group, id and version. The plugin's id is the package's id, so `rookery/unity` is `unity` |
| `about` | `name` is the name Rookery shows, and `summary` its description. Without a name, Rookery shows the id |
| `targets` | `rookery` is the target Rookery installs. `requires` names the Rookery versions the plugin works with |

The ids of plugins and features are lower-case letters, digits, `-` and `_`, starting with a letter. The ids `rookery` and `sign-in` are Rookery's own. The rest of `package.kdl`, such as dependencies and variants for each system, is described in [Hatchery's documentation](https://github.com/aiviarium/hatchery/blob/main/docs/package-kdl.md).

### The Rookery version

The line `rookery ">=0.6"` in `requires` is a range of Rookery versions, in Cargo's syntax. Lines such as `rookery "^0.6" "^0.7"` give a choice of ranges. A package without the line is refused, and so is one for another Rookery: `rookery plugin add` says which versions it wants. A plugin installed before Rookery was updated past its range stays, but Rookery does not use it. `rookery plugin list` shows it as `not used`, with the reason.

### The manifest

`plugin.json` needs `apiVersion`, which is `"1"`, and `name`, the name Rookery and a shell show. The plugin's id and version come from `package.kdl`, and the manifest doesn't repeat them. The JSON Schema [`schemas/plugin.schema.json`](https://github.com/aiviarium/rookery/blob/main/schemas/plugin.schema.json) in the Rookery source describes every field, and a key it does not have is refused. The paths in it, such as `tasks` and `guide`, are relative to the `rookery/` folder.

| Field | Means |
| --- | --- |
| `name` | The name Rookery and a shell show. Required |
| `apiVersion` | `"1"`. Required |
| `description` | One line about the plugin |
| `host` | The host half's entry, a module with `definePlugin` |
| `client` | The client half's entry, a built module a shell loads |
| `styles` | A stylesheet loaded with the client half |
| `dependencies`, `optionalDependencies` | Plugins it needs, by id with a semver range. They activate first. A required one that is missing or out of range keeps this plugin from loading |
| `activate` | `lazy`, the default, or `startup` for a host half that starts with the server |
| `namespace` | The first segment of its routes, its id unless set |
| `contributes` | What it brings: `hostFeatures`, `provisioners`, `shell`, and the parts a shell shows, such as `views`, `nav` and `commands` |
| `provides.services` | The names of the services other plugins may call |
| `interface` | The module that exports `defineInterface`. The extension host loads it before activation |
| `database`, `app`, `services` | Raw SQL for the plugin's own schema, a plugin that is an app of its own, and servers it ships |

`contributes.shell` makes the plugin the server's shell, and holds its entry: `{"entry": "dist/index.html"}`. One plugin on a server has it ([Client halves and the shell](/docs/extend/plugins#client-halves-and-the-shell)).

A plugin written before `plugin.json` has a `rookery.json` with the lists `features` and `provisioners`. Rookery reads it for one more release as a `plugin.json` whose `contributes.hostFeatures` and `contributes.provisioners` are those lists, with the same fields. To convert one, move the lists there, add `apiVersion` and `name`, and remove `rookery.json`: a package with both is refused.

```json title="rookery/plugin.json"
{
  "apiVersion": "1",
  "name": "Unity",
  "contributes": {
    "hostFeatures": [
      {
        "id": "cli",
        "group": "Development Tools",
        "label": "Unity CLI",
        "description": "Shown as help in rookery.",
        "summary": "Unity CLI (`unity`) with its agent skills.",
        "packages": [
          "libgtk-3-0t64"
        ],
        "commands": [
          "unity"
        ],
        "tasks": "tasks/cli.yml",
        "guide": "guide.md",
        "actions": [
          {
            "name": "status",
            "label": "Sign-in and license",
            "run": "unity auth status"
          }
        ]
      }
    ]
  }
}
```

### Host halves

A plugin's `host` names its host half, a module that runs on the server: `export default definePlugin((rookery) => { ... })` from `@rookery/sdk`. Rookery starts it the first time something of the plugin is used, or with the server when the manifest says `"activate": "startup"`. Each plugin's host half runs in a Bun process of its own, and the server knows which plugin a call is from by that process's pipes alone. A host half calls the server's methods as its plugin, so it reaches its own settings, secrets and storage and no other plugin's. [The extension host](/docs/extend/plugins#the-extension-host) has the process, the memory limit and what a host half can read.

Each method it registers with `rookery.rpc.handle` says who may call it through `plugins.rpc`, and one that says nothing is refused:

| `level` | Who may call it |
| --- | --- |
| `own` | A person who is signed in, or the server's own machine. Not another plugin. The handler checks the rest, with `ctx.user` |
| `admin` | An admin |

A job declared in `contributes.jobs` has an ID such as `echo.build`. The host half registers it with `rookery.jobs.handle("echo.build", { run })`, and callers enqueue it as `echo/build`. Use `job.log` and `job.progress` to record output for the current attempt. Return the result from `run`. On cancellation, `job.signal` aborts and its reason identifies the cancellation. Stop any work when that happens. The server renews the claim until the handler stops or the process exits. Set `idempotent: true` only if repeating an interrupted job is safe. The queue can then retry up to `maxAttempts`. Other jobs have one automatic attempt. The declaration's `timeoutSecs` limits each attempt.

A job runs for the server rather than a person. An env call in it names `job.ctx`, and has what the plugin was granted.

The job's `enqueue` sets who may start it. With `own`, the default, signed-in users and the declaring plugin may enqueue it. With `plugin`, only the declaring plugin and admins may enqueue it. With `admin`, only admins may enqueue it.

Use `rookery.connections.list({ type })` and `rookery.connections.get(id)` to read metadata for connections of types your plugin declares. Omit `type` to list all of your plugin's types. `rookery.connections.resolve(id)` also opens the sealed credential and returns it to the declaring plugin's process. Host halves use global connections. The server identifies the plugin from its process, so the host half gives no plugin or user ID. Keep credentials out of logs, service responses and job results.

A host half hears events with `rookery.events.subscribe`. A name without a `/` is its plugin's own, and a full name is another's, such as the server's `rookery/hosts.changed`, `rookery/resources.changed` and `rookery/jobs.changed`.

#### Hosts, files and commands

A host half works with a host through `rookery.env`. Each call takes the context of the handler it serves:

```ts title="host.ts"
rookery.services.provide("notes", {
  read: (ctx, { path }) => rookery.env.readFile(ctx, "studio", path),
})
```

The server runs an env call for the person whose call the handler serves. It checks the call with that person's level on `env://NAME`. Some handlers run on the server's behalf: a job and a service call another plugin made. A service call from the server's own machine does too. Their calls have the plugin's own grants.

A plugin gets a level on a host through a grant on the host, which takes manage on `env://NAME` to make. The principal is `plugin:<id>`: `{"resource": "env://studio", "principal": "plugin:notes", "level": "use"}`. Without a grant of its own, a plugin's call is refused: an `everyone` grant does not reach a plugin. Removing a plugin takes its grants away, so a package that later takes its id starts with none.

| Method | What it does | Level |
| --- | --- | --- |
| `list(ctx)` | The hosts the person may see, as environments | view |
| `get(ctx, env)` | One host, with the person's level | view |
| `presence(ctx, env)` | Who has terminals on a host | view |
| `exec(ctx, env, command, opts)` | Runs a command to its end, with `cwd`, `env`, `stdin` and `timeoutMs`, within the handler's call: 120 s by default, at most 300 s. Its output is at most one message | use |
| `checkouts(ctx, env)` | The git checkouts and worktrees under the host's checkouts folder | use |
| `clone(ctx, env, repository, opts)` | Clones into the host's checkouts folder, with `name` and `branch` | use |
| `worktree(ctx, env, checkout, branch, opts)` | A worktree of a checkout, on a new branch, in the same folder | use |
| `removeCheckout(ctx, env, path, opts)` | A checkout, or a worktree through `git worktree remove`, with `force` for one with changes | use |
| `readFile(ctx, env, path)` | A file inside the host's roots, in base64 with its SHA-256, up to 8 MiB | use |
| `writeFile(ctx, env, path, content, opts)` | Text or bytes, with `ifMatch` and `overwrite` as for a client half | use |
| `deleteFile(ctx, env, path, opts)` | A file, or a folder with `recursive` | use |
| `listDir(ctx, env, path)` | The entries of a folder | use |
| `stat(ctx, env, path)` | The kind, size and modification time of a path, or no entry | use |

On the host, commands and files are the agent account's. A host half cannot choose the operator account or root. A call that asks for one is refused. Files are inside the host's roots, a write is at most 8 MiB, and a checkout stays in the host's checkouts folder.

A host half has no `connect` or `portUrl`: a byte stream or a browser address belongs to a client half's own connection.

#### Data, spaces and access

A handler reads and writes the plugin's collections through the context of the call it serves. The server runs those calls as the person the invocation is for, so the person's own access decides what a handler sees and changes. A job, and a call another plugin made, has no person and runs at the plugin's own level.

```ts title="host.ts"
rookery.services.provide("notes", {
  list: (ctx, { space }) => ctx.data.space(space).notes.find({}),
  share: (ctx, { uri, person }) => ctx.access.grant(uri, `user:${person}`, "view"),
})
```

`ctx.data` is the plugin's collections for the person, and `ctx.data.space(id)` is the same in a space. `rookery.data` is the plugin itself: its own collections as their admin, whatever the handler serves. Its rows of another plugin's collection are only those a grant of its own reaches.

`ctx.space` is the space the caller's connection entered, or `null`. A collection of a space is named by `ctx.data.space(id)` when the handler means one that is not the caller's current.

| On the context | What it does |
| --- | --- |
| `data.<collection>.find`, `get`, `count`, `search`, `aggregate`, `scan`, `insert`, `update`, `upsert`, `delete`, `restore`, `purge`, `batch`, `import`, `history`, `tail` | The collections, as for a client half |
| `data.refs` | `to(uri)` and `from(uri)`: what refers to an entity and what it refers to |
| `data.changes.subscribe(collection, fn)` | Every change of one collection the person may read, as `{collection, op, id, row, seq}`; it ends with the call |
| `data.space(id)` | The collections in a space |
| `access.level(resource)`, `access.check(resource, level)`, `access.require(resource, level)` | What the person holds on a resource |
| `access.filter(resources, level)` | Those of some resources the person holds a level on |
| `access.grant(resource, principal, level)`, `access.revoke(resource, principal)`, `access.grants(resource)` | Sharing, for a person who holds manage |
| `access.levelOf(resource, user)` | What another person holds, which is the plugin's own question |

The rest of the handle takes the context of the handler, and runs as its person:

| Handle | What it does |
| --- | --- |
| `spaces.list(ctx)`, `get`, `create`, `rename` | The spaces the person may see, and making one of a kind a plugin contributes |
| `entities.lookup(ctx, uri)`, `lookupMany`, `search`, `text` | The entity index, as far as the person may see it |
| `entities.register`, `remove`, `alias` | The plugin's own entities, in a scheme it declares |
| `documents.list`, `create`, `edit`, `delete`, `read`, `convert` | Documents, read at `view` and edited at `use` |
| `users.search(ctx, resource, text)` | People to share a resource with, for a person who holds manage on it |
| `blobs.put(ctx, data, opts)`, `get`, `delete` | Files of up to 8 MiB, whoever the person is |
| `audit.list(ctx, query)` | The audit log, for a person who is an admin |
| `schedules.create(ctx, …)`, `list`, `setEnabled`, `fire`, `remove` | The person's own recurring jobs, never another's |
| `terminals.list(ctx)`, `get`, `screen`, `write`, `close` | The person's terminals, at their level on the host |

Two handles stay the plugin's own, whoever the handler serves: `sql.query`, `sql.execute` and `sql.begin` are the schema the plugin owns and needs `database.sql` in the manifest, and `audit.record` records an action under the plugin's id, its `resource` being free text a reader should not take as proof. `blobs.read` needs the server's stream channel to a host half, which this version does not serve.

A handler's call is checked as the person it serves, and a person's own schedules, blobs and terminals are theirs alone. A plugin cannot name a user: the server binds the call to the invocation, refuses a call whose invocation has ended, and ends the change feeds the handler started when the call does.

#### Host services

List each service name in `provides.services` and point the manifest's `interface` field at the module that declares its methods. Use the same declaration when registering the service:

```ts title="interface.ts"
import { defineInterface, z } from "@rookery/sdk"

export default defineInterface({
  services: {
    greeter: {
      hello: {
        params: z.object({ name: z.string() }),
        result: z.string(),
        timeoutSecs: 5,
      },
    },
  },
})
```

```ts title="host.ts"
import { definePlugin } from "@rookery/sdk"
import api from "./interface"

export default definePlugin((rookery) => {
  rookery.services.provide(api.services.greeter, {
    hello: (_ctx, { name }) => `Hello, ${name}`,
  })
})
```

Other host halves and client halves call `rookery.services.call("echo", "greeter", "hello", { name: "Ada" })`. Set `provides.serviceLevels.greeter` to control access:

| Level | Who may call it |
| --- | --- |
| `own` (default) | Signed-in users and plugins |
| `plugin` | Plugins and admins |
| `admin` | Admins |

A host service can read the caller's identity from `ctx.principal`. The interface validates the input and the result. `timeoutSecs` sets the method's time limit, up to 300 seconds. Methods use the server's call timeout by default.

Declare `stream: true` for a method that yields chunks from an async generator. Each chunk matches the declared `result` schema. Host callers iterate over `rookery.services.stream(plugin, service, method, params)` with `for await`. Client callers use the same arguments to open a stream of newline-delimited JSON.

A plugin may also implement a service with one of its app services in `services`. An admin places the app service at a URL with `services.setExternal`. The server calls it with JSON-RPC over `POST URL/rpc`, using its secret as a bearer token. A method in `contributes.rpc` with a `handler` routes to an app service or to the host half's service of that name. A plugin's `extensionPoints` take contributions from other plugins under `contributes.extensions`, which `extensions.list` gives when they match the point's schema.

A method in `contributes.rpc` declared `"stream": true` is opened with `plugins.rpc.stream`, by a client half or a host half, and answers as a stream of JSON values. A host service yields them from an async generator, with the credit and cancellation of a service stream. An app service gets `"stream": true` in its call and answers `application/x-ndjson`: each line is a JSON-RPC message, a `result` is one item, an `error` ends the stream, and a line with neither ends it well. The entry's `timeoutSecs` bounds the whole stream, 30 seconds unless it says otherwise, up to 300. `plugins.rpc` refuses a method declared as a stream, and `plugins.rpc.stream` refuses one that is not. Either routes to the host service or the app service that provides the name, as `services.call` does.

A host half is ended, and counted as a crash, when its process ends or when a handler keeps running past its call's deadline. So is one whose process holds more memory than `ROOKERY_EXTHOST_MEMORY_MB` (512 MiB unless set). After five crashes in a minute it's failed. Then only an admin starts it again, also as a dependency of another plugin.

### Client halves

A plugin's `client` names a built module that a shell loads in the browser, and `styles` a stylesheet beside it. A client half exports `defineClient` from `@rookery/sdk/client`:

```ts title="rookery/client.js"
import { defineClient } from "@rookery/sdk/client"

export default defineClient((rookery) => {
  rookery.views.register("hello.main", () => <p>Hello</p>)
})
```

The files are served at `/plugins/{id}/{hash}/{path}`, where `hash` is the SHA-256 of the client half's files. Those are the entry's folder, so a client half with more than its entry keeps them in one, such as `client/`. An entry at the top of the target is served alone, as the folder beside it holds the rest of the plugin. A browser keeps a version for good, and a new version has an address of its own. The route serves only those files and the stylesheet, and it needs no sign-in, as a page loads a shell before anyone signs in. Put nothing secret in a client half.

`plugins.list` gives the `client.script` and `client.styles` addresses, and a shell loads them. A client half calls its host half with `rookery.rpc.call`, and hears the server's events with `rookery.events.subscribe` under their full name, such as `rookery/hosts.changed` ([Server events](/docs/extend/plugins#server-events)).

## Actions

An action becomes an action of the host's controller named `PLUGIN:ACTION`. Applying the configuration writes the actions of the chosen features to the host, and `rookery action list HOST` lists them in their group. They run with `rookery run HOST PLUGIN:ACTION`.

### Arguments

The command finds each argument as `ROOKERY_ARG_NAME` in its environment, upper-cased, with `_` for anything that is not a letter or digit. Values are never pasted into the command line. `choices` is a command whose output lines are the values to offer. `values` and `kind` mean what they mean for a provisioner's arguments, below. A yes or no is a switch here too.

### Steps of other actions

An action with `extends` has no row of its own. It runs after the action it extends, every time, and its output follows that action's. Start that output with the plugin's name. An action and its steps run one after another in one session, each as its own user. All steps run even when one fails. `rookery run HOST status` includes what plugins add to it.

### Terminal actions

An action with `terminal: true` takes the terminal it runs in, over `ssh -t`, as a sign-in does. Actions without it have no terminal, so make them non-interactive.

Sign-ins should not open a browser on the host. Start them with `env -u DISPLAY BROWSER=echo` so the tool prints its link.

<Callout type="warn">
  Leave `agent` off for anything the agent should not start, and think twice before setting it on an action that runs as `root`.
</Callout>

## Tasks

`tasks` is a plain Ansible task list, included while the role runs: after the base tools and coding agents are installed, before the desktop is configured. Features are applied in the order the plugin lists them, so a later one can rely on an earlier one. The tasks can use these variables:

| Variable | Value |
| --- | --- |
| `rookery_user`, `rookery_home` | The agent's account and home |
| `rookery_plugin_dir` | The plugin's `rookery/` folder, for files it brings |
| `rookery_plugin_features` | Every feature chosen for the host |
| `rookery_software_rendering`, `rookery_profile` | And the other `rookery_` settings |

A plugin's tasks use only their own files, through `rookery_plugin_dir`. They do not reach into the role, so a `.yml` file of the plugin that names `role_path`, `playbook_dir` or `inventory_dir` fails the [check](#checking-a-plugin).

A setting of your own, such as a version, can be given per host in the profile's `ansible_vars` as long as its name starts with `rookery_`. Read it with a default:

```yaml
version: "{{ rookery_unity_cli_version | default('1.0.0-beta.17') }}"
```

Tasks must be safe to run again, because applying a configuration runs them every time.

On a [node](/docs/use/nodes) there is no agent: `rookery_user` and `rookery_home` are the SSH user and its home, and `rookery_level` is `node`. A feature for a node can also set these:

| Fact | What it adds |
| --- | --- |
| `rookery_firewall_rules` | Rules of the node's firewall, as the arguments of `ufw`, such as `allow in on incusbr0`. The role deletes a rule of a feature that the node no longer has |
| `rookery_node_units` | Units whose state rookeryd reports, such as `incus` |
| `rookery_offer` | The provisioners it offers, once the tasks are sure of them |

### Offering provisioners

A feature that lists `offers` sets `rookery_offer` with `set_fact` at the end of its tasks. The role keeps it in the host's `/etc/rookery/applied.json`, and Rookery registers a provisioner of each type after the apply, with the node it is on. The record is readable on the node, so it holds public values only. Rookery takes the provisioners the feature lists in `offers`, with their own arguments and secrets. It ignores any other provisioner, setting or secret in the record.

A provisioner registered by hand becomes the node's when Rookery finds the server it names on the node's address and port. The node's word alone, its aliases or the certificate it reports, never changes another provisioner. The apply then names it, and `rookery provisioner run NAME adopt node=NODE` makes it the node's.

| Field | Meaning |
| --- | --- |
| `provisioners` | The ids it offers now, out of `offers`. All of them when it is left out |
| `settings` | Values of the provisioners' own arguments. `{address}`, `{user}` and `{port}` become where Rookery reaches the node and as whom. A URL has to name the node's address |
| `secrets` | Values of the provisioners' secrets, such as a server's certificate, kept as each provisioner's own |
| `aliases` | Other values of a setting that reach the same server. A provisioner registered by hand with one is named in the apply's output, and its owner can make it the node's |
| `fingerprint` | What identifies the server, for the apply's output |

```yaml
- name: Offer the provisioner of this engine
  ansible.builtin.set_fact:
    rookery_offer:
      provisioners: [container]
      settings:
        host: "ssh://{user}@{address}:{port}"
```

With `trusts`, the certificate is in `rookery_client_certificates`, under the feature's `PLUGIN/ID`, with its `fingerprint` and a `name` for the trust store.

## Guide

The guide is installed as `/etc/rookery/guides/PLUGIN-FEATURE.md` and linked from the host's `AGENT.md` ([On the host](/docs/reference/on-the-host#what-agents-read)). It is a Jinja template, so it can adapt to the host:

```md title="guide.md"
{% if rookery_software_rendering %}
This machine renders on the CPU; pass `--software`.
{% endif %}
```

Write it for an agent that has never seen the tool. Cover what the command is and what has to happen before first use. Then say what needs a person, and what the agent must not ask about again.

## Channels

A feature that publishes on the host's channel lists its topics with how long the host keeps them:

```json
"channels": [{"topic": "progress", "keep": "none", "max": 1000, "days": 30}]
```

The topic becomes `PLUGIN/TOPIC`. `keep` is the default for messages published there. With `none` only current listeners see a message, `last` stores the newest one, and `log` stores them for reading later. `max` and `days` limit a log. Publish with `box publish PLUGIN/TOPIC '{"percent": 40}'` and read with `box listen PLUGIN/`.

## Writing a provisioner

A provisioner is a program of a plugin that makes things on a platform: machines for saved hosts, and other kinds of things its plugin names. It also has actions of its own, such as listing images or freeing space. Its plugin lists it under `contributes.provisioners` in `plugin.json`, next to `hostFeatures`, and holds the executable in its `rookery/` folder. People register it under a name of their own with `rookery provisioner add NAME PLUGIN/ID`, and then use it with `rookery host create HOST --provisioner NAME`, `rookery provisioner show NAME` and `rookery resource list` ([Provisioners](/docs/deploy/provisioners), [Resources](/docs/deploy/resources)). The plugins `docker` and `incus` in the Rookery source are examples.

```json title="rookery/plugin.json"

  "name": "Lab",
  "contributes": {
    "provisioners": [
      {
        "id": "vm",
        "label": "Lab virtual machine",

        "command": "bin/provision",
        "protocol": 2,
        "verbs": [
          "list"
        ],
        "secrets": [
          "lab_token",
          {
            "name": "lab_ca",
            "required": false
          }
        ],
        "arguments": [
          {
            "name": "server",
            "label": "Lab server",
            "required": true
          }
        ],
        "kinds": [
          {
            "id": "machine",
            "setup": "seed",
            "archive": true,
            "verbs": [
              "start",
              "stop",
              "change",
              "logs"
            ],
            "arguments": [
              {
                "name": "cpus",
                "label": "CPUs",
                "default": "4",
                "kind": "resource"

              {
                "name": "image",
                "label": "Image",
```

### Collections

A collection is a list of things the provisioner holds, such as the storage pools of a server, its volumes or its images. The provisioner's page shows each as one row with the number of its items. Enter opens a table of them, and each item has a page with the actions that act on it. Its actions are the provisioner's own, declared in `actions` as usual. A collection lists the ones that belong to it in `new`, `item` and `list`, and the page offers them there and not as rows of their own. `rookery provisioner run` runs them as any other action, and `rookery provisioner show` prints each collection as a table.

The Incus plugin declares its pools and the volumes in them:

#### A yes or no

Declare a yes or no with `"kind": "boolean"`, and give its two values too:

```json
{"name": "keep_volumes", "label": "Keep volumes", "default": "no", "kind": "boolean", "values": ["no", "yes"]}
```

The set-up asks for it as a yes or no. An argument whose `values` are just `yes` and `no`, or `true` and `false`, is a switch as well. Your program gets the value for on or off from `values`, or `yes` and `no` without them. On the command line it is given as one of these, in any case, and Rookery sends the declared value:

| On | Off |
| --- | --- |
| `yes`, `true`, `on`, `1` | `no`, `false`, `off`, `0` |

An action's `confirm` question names each switch that is on. Give the argument a `confirm` of its own, such as `"confirm": "Remove the deployment and its volumes?"`, and Rookery asks that question instead of the action's while the switch is on.

A provisioner's `status`, described below, lists the values an argument takes. Rookery does not run a `choices` command for a provisioner.

A host's set-up tabs show the arguments of a machine: the provisioner's own first, then the machine kind's.

| Argument | Where Rookery shows it |
| --- | --- |
| `required` | With the way to install, under the provisioner |
| `"kind": "resource"`, not required | With the machine's size, in the settings |
| Any other | With the provisioner's other options, in the settings |

Rookery checks the value of a resource before it creates the machine. It goes by the name of the argument:

| Name contains | The value has to be |
| --- | --- |
| `cpu` | A positive number, such as `4` |
| `memory`, `mem`, `ram`, `disk`, `size`, `storage` or `swap` | A size with its unit, such as `8GiB`, `512MiB` or `4g` |
| anything else | Not checked |

An argument that is not required may be left empty. Rookery lists a bad value as a problem of the part of the set-up that shows the argument, but the command line does not check resources. The provisioner checks what it is given in any case.

### How it is run

Rookery runs `COMMAND VERB` directly, with the plugin's `rookery/` folder as its working directory and in a process group of its own. Give the file a shebang and the executable bit.

| Channel | Use |
| --- | --- |
| Standard input | One JSON object, the request, which holds the secrets |
| Standard output | One JSON object, the answer. Empty output is read as `{}`. `logs` writes the log here instead |
| Standard error | Progress. Each line is shown as it comes |
| Exit code | 0 is success. Anything else is a failure, and the last five lines of standard error are the reason |

When the command ends, Rookery ends everything it started in the process group. Do not leave anything running in the background.

| Verb | Time allowed |
| --- | --- |
| `status`, `list`, an `act` that only reads | 30 seconds |
| `start`, `stop`, `destroy`, `change` | 5 minutes |
| `create`, `exec`, an `act` that changes something | 15 minutes |
| `logs` | Until it ends, or the one who asked stops reading |

A command that takes longer is killed with its group.

### The request

Every verb gets this:

| Field | Value |
| --- | --- |
| `version` | `2`. A provisioner refuses another version |
| `verb` | The verb |
| `provisioner` | The id within the plugin, so one command can serve several provisioners |
| `arguments` | The values of the arguments that apply, with defaults filled in. The provisioner's own come from what was given or from its settings. A verb about a machine also gets those of the machine kind |
| `secrets` | The secrets it names that have a value |

A verb about one resource also gets these. `status` without an `id`, `list` and an action of the provisioner itself are about the provisioner and have none of them. An action of a kind is about one resource and has them.

| Field | Value |
| --- | --- |
| `kind` | `machine`, or the kind's id |
| `name` | The resource's name. A machine's is the host's |
| `host` | The host's name, for a machine |
| `id` | The id `create` answered with, once it has |
| `labels` | For a machine, `rookery-host` with the host's name and `rookery-instance` with the token. For another kind, `rookery-resource` with Rookery's id of the resource and `rookery-token` with the token |
| `node` | The node the provisioner is on, when a node's apply registered it. The node's controller dials its endpoints |

The verbs about a resource get the `arguments` that `create` was given, with defaults for any argument added since. A resource of any other kind gets the provisioner's own arguments and its kind's.

Each verb adds to it and answers like this:

| Verb | Request adds | Answer |
| --- | --- | --- |
| `create` | `token`. For a machine, `seed` or `access`. For another kind, `environment`, and `spec` when the kind has one | `id`, and optionally `address`, `port` and `endpoints` |
| `status` | `id` | `state`, which is `running`, `stopped` or `gone`, and optionally `address` and `endpoints`. Rookery shows `gone` as `missing` |
| `status` | nothing | The provisioner itself: `state` (`ready` unless it says otherwise), `message`, `details`, `values`, `collections` |
| `destroy` | `id` | `{}` |
| `start`, `stop` | `id` | `{}`, and optionally `state` and `endpoints` |
| `change` | `id`, the new values in `arguments`, `changed` with the names of the arguments whose value is new, and `environment`. For a kind with a specification, `spec`: the new one, or the one Rookery has | `state`, and optionally `endpoints` |
| `exec` | `id`, `command` as a list of words, and `stdin` when there is input | `exit_code`, the command's exit status. Its output goes to standard error |
| `logs` | `id`, `tail` and `follow` | The log on standard output, a line at a time, until it ends |
| `list` | nothing | `resources`, a list of `id`, `kind`, `name`, `host` and `state`, of every kind |
| `act` | `action`: its `name` and its `arguments`. For an action of a kind, also `environment`, and `spec` when the kind has one | `message`, and optionally `details` |

`create` must answer with an `id`. Rookery keeps it, and every later verb uses that id. For a machine, the `address` and `port` go into the profile's `access.address` and `access.port` when those are empty. Entries of `list` without an `id` are dropped. An entry without a `kind` is a machine, and one without a `name` takes its `host` as its name.

`spec` is the specification as the person gave it, as text. `environment` maps variables to the values of the Rookery secrets the resource is given, such as `{"DB_PASSWORD": "…"}`. It is empty for a resource without secrets. Pass these values on only through the environment of the program that needs them, and Rookery masks them in your output as it does secrets.

For `logs`, `tail` is how many of the last lines to give, and `follow` whether to go on with what comes after them. Give a machine's console, or its boot output when the console has none. An empty log is no failure.

While Rookery waits for a new machine, it asks `logs` of the machine kind with each `status`, until SSH answers, with `tail` at 100 and `follow` false. It shows the lines it has not shown before. Rookery removes escape sequences and control characters, shortens long lines and shows at most six lines at a time. It hides the provisioner's secrets and those of the seed. A kind without `logs` is waited for without them.

### Endpoints

An answer about one resource may report where it is reached, as `endpoints`. Rookery keeps the list with the resource's record, and an answer with `endpoints` replaces it whole. An answer without them leaves the list as it was, and a resource that is gone has none. Report them from `create`, `status` and `change`, so they follow what is there, and from `start` and an `act` that makes it anew when those know.

```json title="Answer of status"
{"state": "running",
 "endpoints": [{"name": "8080", "address": "127.0.0.1", "port": 8080, "hint": "http", "local": true},
               {"name": "bridge-80", "address": "172.17.0.2", "port": 80, "hint": "http", "local": true}]}
```

| Field | Value |
| --- | --- |
| `name` | Unique within the resource. Lowercase letters, digits, `-`, `_` and `.`, up to 63, starting with a letter or a digit |
| `address` | An IP address or a DNS name, as seen from the machine your engine runs on |
| `port` | 1 to 65535 |
| `protocol` | `tcp`, the default, or `udp` |
| `hint` | What speaks there, such as `http` or `postgres`. Rookery shows it to people and doesn't read it |
| `local` | `true` when your engine runs on the machine that dials: the one Rookery runs on, or the node in the request |

Rookery leaves out an endpoint that does not fit, and the first of two with the same name stands. `resources.connect` dials only what you report. It dials from the server, or from the node when the request has `node`. Report `local` only for an engine on the server's own machine or on that node, as a loopback address is then the dialling machine's. With `node`, report addresses as the node sees them: `127.0.0.1` for a port published on every address, and the addresses of the node's bridges. For an engine elsewhere, report addresses that other machines can connect to, such as a port published on the engine's own name. Leave out the addresses only its machine routes to.

### Commands

A kind with `exec` among its verbs gets Rookery's action `exec` ([Run a command in it](/docs/deploy/resources#run-a-command-in-it)). Rookery sends the command as a list of words in `command`, never as one line for a shell. Run it as it is, with `stdin` on its standard input when the request has it. Write its output to standard error as it comes. Answer with its `exit_code`. Exit with 0 even when the command fails; exit with another code only when you could not run it, such as when the resource is not running. Rookery records the command line in the job, and not the input.

`details` is a list of rows, each `{"label": …, "value": …}`, which Rookery shows as they are, such as a pool and how full it is. `values` names, by argument, the values an argument takes here, such as `{"pool": ["default", "fast"]}`. Rookery offers those in place of what the manifest says.

`collections` gives the items of each [collection](#collections), by its id. An item has a `name` and a `key` with a value for each part. Its `columns` hold its values by name. `unavailable` gives the item actions that cannot run on it, each with why not. The key of a collection whose key has one part may be left out: it is the name. Rookery leaves out an item without its whole key, and a collection left out of the answer is shown as not listed.

```json
"collections": {
  "pools": [
    {"name": "default", "columns": {"driver": "zfs", "size": "100.0 GiB"}},
    {"name": "fast", "columns": {"driver": "dir", "size": "200.0 GiB"},
     "unavailable": {"resize-pool": "A dir pool has no size of its own"}}
  ],
  "volumes": [
    {"name": "data", "key": {"pool": "default", "volume": "data"}, "columns": {"size": "10GiB"}}
  ]
}
```

A `status` without an `id` that fails is shown as `unreachable`, with the reason. Answer it quickly, because Rookery asks it each time the provisioner's page opens.

A `seed` provisioner also receives the cloud seed with `create`:

| Field | Value |
| --- | --- |
| `seed.user_data` | The cloud-init user data |
| `seed.meta_data` | `instance-id` and `local-hostname`, as text |
| `seed.archive` | With `archive: true`: `path` of the release archive on the machine Rookery runs on, and its `sha256` |

An archive has to end up as `/opt/rookery-bootstrap/release.tar.gz` in the machine. First boot waits up to 15 minutes for the file to have that digest.

An `apply` provisioner receives `access`: the `user` to create and the `public_keys` that may log in as it. It must make SSH answer for that account.

### Rules

A provisioner is run again after a crash or a timeout, and it works on machines that belong to people. Keep these rules:

- **Create once per token.** Called again with the same `token`, `create` answers with the machine it made before and does not make a second one.
- **Label what you make.** Put `labels` on the machine in whatever way the platform allows.
- **Destroy a machine that is gone.** `destroy` succeeds when there is nothing left to delete, and deletes only the machine with the `id` it is given.
- **Leave alone what lacks Rookery's labels.** `list` shows, and `destroy`, `change` and the actions touch, only what has them. An action that frees space removes only what Rookery made.
- **Write progress to standard error.** Standard output is for the answer.
- **Take secrets from standard input only.** That includes the values in `environment`. Never print them, and do not put them on a command line or in a file that stays after the command ends. Rookery hides secrets in the lines you write, but it cannot hide what you write elsewhere.

### Try it

Install the plugin from its folder and see that Rookery finds the provisioner and what it says of itself:

```bash
rookery plugin add ~/src/lab
rookery provisioner types
rookery provisioner add lab lab/vm server=https://192.0.2.10:8443
rookery provisioner show lab
```

Run a verb by hand from the plugin's `rookery/` folder with a request on standard input. Use a scratch machine and made-up values:

```bash
echo '{"version":2,"verb":"status","provisioner":"vm","arguments":{"server":"https://192.0.2.10:8443"},"secrets":{}}' \
  | bin/provision status
```

Then create a machine for a saved host and delete it again:

```bash
rookery host create studio-2 --provisioner lab/vm
rookery resource list                       # the machine's id, such as r-k3q7wz2m
rookery resource remove r-k3q7wz2m
```

Run `rookery host create --provisioner` a second time while the first has failed to check that it finds the same machine.

## Checking a plugin

```bash
rookery plugin check ./hello
```

`rookery plugin check` packs the folder as `rookery plugin add` does and checks it against Rookery's plugin contract. It works without a server. It prints each problem with the file it is in and exits with status 1 when there is one. Given the folder of a static registry, one with an `index.json`, it checks each package the registry lists, as Rookery's CI does with `rookery plugin check plugins`.

| Checked | Rule |
| --- | --- |
| `package.kdl` | It reads, has a `rookery` target and a valid id, and names the Rookery versions in `requires` |
| `plugin.json` | It matches `schemas/plugin.schema.json`, or a `rookery.json` matches `schemas/rookery-plugin.schema.json`. Host feature, provisioner, view, command and setting ids are unique |
| Halves | `host`, `client`, `styles` and a shell's `entry` name files in the `rookery/` folder, and each dependency has a version range |
| Files | Each `tasks`, `guide` and provisioner `command` names a file in the `rookery/` folder |
| `offers` | Each id is that of a provisioner of the same plugin |
| Ansible files | No `.yml` or `.yaml` file names `role_path`, `playbook_dir` or `inventory_dir` |

Rookery checks a package the same way when it installs it. A repository of plugins can run `rookery plugin check` for each one in CI. Without Rookery, Hatchery checks the schema alone:

```bash
hatchery pack hello --base --out dist --check rookery=rookery-plugin.schema.json
```

## Sharing a plugin

A git repository with a `packages.kdl` at its root is a plugin registry. Each package is a folder of it, and each version a tag:

```kdl title="packages.kdl"
format 1

packages {
  find "*"
}

release {
  tag "{id}-v{version}"
}
```

Tag a release with the package's id and the version in its `package.kdl`, such as `hello-v1.0.0`, and push the tag. Hatchery installs a plugin with no build command straight from the tag. Others add the repository with `rookery plugin registry add git URL` and install the plugin by its name. [Hatchery's documentation](https://github.com/aiviarium/hatchery/blob/main/docs/registries.md) describes the other kinds of registry, built eggs and signing.

A repository of one plugin, with its `package.kdl` at the root, doesn't need a `packages.kdl`: `rookery plugin add --git URL --ref TAG` installs it.
