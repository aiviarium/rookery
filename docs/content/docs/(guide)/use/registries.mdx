A registry is a server with one address and one login. Hosts get npm and Docker logins from registries, and Rookery publishes the release archive and the container image to them.

| Kind | What it is | Used for |
| --- | --- | --- |
| `nexus` | A Sonatype Nexus server, with repositories under it | Whatever its repositories are for |
| `npm` | Any npm-compatible registry at an address | The agent's npm registry and its login |
| `raw` | An address files are uploaded to with HTTP PUT | Publishing the release archive |
| `docker` | Any container registry, as `HOST` or `HOST:PORT` | Pushing the container image, the agent's Docker login |

A registry with a user name logs in with user name and password. Without a user name, what is stored is used as a token: `_authToken` for npm, a bearer token for uploads.

Registries, with their addresses and user names, are kept in the server's database. Passwords and tokens are kept there as secrets, sealed with the server's key.

## Adding registries

```bash
rookery registry add nexus nexus https://nexus.example.com --user ci-user
rookery registry login nexus                      # asks for the password or token
rookery registry add-repo nexus npm npm-group
rookery registry add-repo nexus raw rookery-releases
rookery registry add-repo nexus docker docker-hosted --address nexus.example.com:8083

rookery registry add verdaccio npm https://npm.example.com     # token login
rookery registry add files raw https://files.example.com/rookery --user ci-user
rookery registry add ghcr docker ghcr.io --user my-user

rookery registry list                                  # the list
rookery registry check                            # do they answer and accept the login?
```

`rookery registry remove` takes a registry away again, and its repository and login with it. `rookery registry check` checks that the server answers, that each repository exists and is readable with the stored login, and that a Docker address speaks the Docker API. It only reads, so it does not show whether the account may upload.

### Nexus repositories

| Format | Address | Used for |
| --- | --- | --- |
| `npm` | `URL/repository/NAME/` | The agent's npm registry and its login |
| `raw` | `URL/repository/NAME/` | Publishing the release archive |
| `docker` | `HOST/NAME`, or the address you give | Pushing the container image, the agent's Docker login |

A Docker repository with path-based routing in Nexus does not need an address: images are at `HOST/REPOSITORY/IMAGE`. With a connector on a port or host name of its own, give that address. Maven repositories are not handled.

## Giving a host a registry

```bash
rookery host set studio registry.nexus=on
rookery run studio secrets
```

Or switch it on with `rookery host set studio registry.nexus=on`, then send the logins with `rookery run studio secrets`. The agent's `~/.npmrc` gets the first npm repository as its registry with the login, in a block Rookery manages. The rest of the file is kept. `~/.docker/config.json` gets the login of every Docker address.

## Publishing the release archive

A machine set up from a [cloud seed](/docs/deploy/cloud) downloads the release archive. With the cloud seed as the method, `release_store` names a file server or raw repository of the registries, and `release_private` decides whether the machine logs in for the download. Making the seed then uploads the archive and points the seed at it:

```bash
rookery registry publish nexus/rookery-releases --host cloud-1
rookery registry publish files --host cloud-1
```

Either way the seed pins the archive's SHA-256, and the archive contains no profiles, keys or secrets. The new machine downloads it with or without a login.

<Tabs items={['Without a login', 'With a login']}>
<Tab value="Without a login">

The default. The repository has to allow anonymous reads.

</Tab>
<Tab value="With a login">

```bash
rookery registry publish nexus/rookery-releases --host cloud-1 --login              # the login of nexus
rookery registry publish nexus/rookery-releases --host cloud-1 --login nexus-read   # another registry's
```

The cloud seed then contains that login, in a file only root can read that is deleted after the download. The login is taken from your machine when the seed is rendered, so it is never written into the host's profile.

<Callout type="warn">
  Whoever can read the seed can read the login: your cloud provider's console, and the machine's metadata service until it is removed. Use an account that may only read that repository. A second registry entry for the same server with such an account does that.
</Callout>

</Tab>
</Tabs>

## Pushing the container image

```bash
rookery registry push-image nexus/docker-hosted          # NEXUS-DOCKER-ADDRESS/rookery-desktop:latest
rookery registry push-image ghcr v1                      # ghcr.io/rookery-desktop:v1
```

pushes the image built by the **Container image** install method.
