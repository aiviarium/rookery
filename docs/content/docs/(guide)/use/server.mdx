A server machine keeps the hosts with their profiles and secrets, and runs `rookery serve`. Rookery on another machine, such as your laptop, then uses that server: `rookery ls`, `rookery apply` and every other command call the server's API on its [`/ws`](/docs/api#the-servers-methods). On macOS and Windows Rookery is only that: a client of a server.

```text
 your laptop                  the server                       hosts
┌─────────────┐  HTTPS/HTTP  ┌───────────────────────────┐ SSH ┌─────────┐
│ rookery     │ ───────────▶ │ rookery serve             │ ──▶ │ studio  │
│ rookery ls  │  + sign-in   │ PostgreSQL: hosts, jobs,  │ ──▶ │ cloud-1 │
└─────────────┘              │ secrets, accounts         │     └─────────┘
                             └───────────────────────────┘
```

## What the server needs

| What | Why |
| --- | --- |
| PostgreSQL | The hosts, jobs, secrets, accounts and plugins. A database of its own, or the one the image runs |
| SSH to each host | An apply, a session and an action reach the host over SSH ([Accounts and sudo](/docs/use/accounts)) |
| An address people reach | The server speaks plain HTTP. A TLS proxy such as Tailscale Serve or Caddy gives it `https` |
| A secret key | A file with 64 hex digits, which seals the secrets in the database ([The secret key](/docs/use/store#the-secret-key)) |

## Run it with compose

This is the documented path: the server in its container, with a PostgreSQL service of its own. Write this file where you keep the server's settings:

```yaml title="compose.yaml"
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: rookery
      POSTGRES_PASSWORD: CHANGE_ME_EXAMPLE
      POSTGRES_DB: rookery
    volumes:
      - db:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U rookery -d rookery"]
      interval: 2s
      timeout: 3s
      retries: 30

  rookery:
    image: ghcr.io/aiviarium/rookery
    depends_on:
      db:
        condition: service_healthy
    environment:
      ROOKERY_DATABASE_URL: postgres://rookery:CHANGE_ME_EXAMPLE@db:5432/rookery
      ROOKERY_PUBLIC_URL: https://rookery.example.ts.net
      ROOKERY_SECRET_KEY_FILE: /config/rookery/secret.key
    volumes:
      - rookery-config:/config
      - rookery-data:/data
      - ~/.ssh:/home/rookery/.ssh:ro
    ports:
      - "127.0.0.1:7777:7777"
    stop_grace_period: 30s

volumes:
  db:
  rookery-config:
  rookery-data:
```

The image runs as user `rookery` (uid 1000) and its `/config` volume is its configuration folder. Make the key in that volume before the first start:

```bash
docker compose run --rm --entrypoint sh rookery -c \
  'mkdir -p /config/rookery && (umask 077; od -An -tx1 -N32 /dev/urandom | tr -d " \n" > /config/rookery/secret.key)'
```

Then start the stack and make the first admin's link:

```bash
docker compose up -d --wait
docker compose exec rookery rookery server setup-key
```

`/` answers with a page that says no shell is installed, until a plugin that contributes a shell is installed, or `ROOKERY_SHELL_DIR` names a built one ([Plugins](/docs/extend/plugins#client-halves-and-the-shell)).

`ROOKERY_PUBLIC_URL` is the address a browser uses, and the address in the sign-in link. A link made with the wrong one opens nowhere. Keep it in step with the published port and the proxy in front. Without a proxy, set it to `http://127.0.0.1:7777` and open the link on the server.

The database is on the compose network alone, with no published port. Its password is in the compose file, so keep that file private. To reach the database by hand, add a `ports` entry on `db` for the time of the work.

## Run it without a database of your own

The image can run a PostgreSQL 17 of its own, in `/data/rookery/postgres`, reached on a socket inside the container. It makes the database and the secret key the first time it starts. Leave `ROOKERY_DATABASE_URL` on the image's own value:

```bash
docker run -d --name rookery -p 127.0.0.1:7777:7777 \
  -e ROOKERY_PUBLIC_URL=http://127.0.0.1:7777 \
  -v rookery-config:/config -v rookery-data:/data \
  -v ~/.ssh:/home/rookery/.ssh:ro \
  ghcr.io/aiviarium/rookery
docker exec rookery rookery server setup-key
```

The link names `127.0.0.1:7777`, so open it on the server, or set `ROOKERY_PUBLIC_URL` to the address a browser elsewhere uses.

This is the shortest way to try a server. The database is in the `rookery-data` volume, so back up that volume, or move to a database of its own before you depend on it. Give the container 30 seconds to stop both, with `docker stop -t 30`. A data folder of another major version of PostgreSQL is refused: dump it with the image that made it, and restore the dump.

## Run it as a program

On Linux, where Rookery is installed, `rookery serve` is the same server without a container. It needs a PostgreSQL database, which it migrates when it starts:

```bash
export ROOKERY_DATABASE_URL=postgres://rookery:PASSWORD@db.example.org/rookery
export ROOKERY_SECRET_KEY_FILE=/etc/rookery/secret.key
export ROOKERY_PUBLIC_URL=https://rookery.example.ts.net
rookery serve
```

Give the variables to the server's service manager, not to a shell on someone's terminal. [`rookery serve`](/docs/extend/serve#its-settings) lists every variable it reads. Several servers can run on one database: one leads, and the others stand by.

A machine with Docker also runs the server from an image built from a checkout of Rookery, over SSH:

```bash
rookery server deploy ops@192.0.2.10
```

`rookery server deploy` sends the image's context to the machine, builds it there with its Docker engine, and starts the container on `127.0.0.1:7777` of that machine. `--release VERSION` pulls the published image instead, `--port PORT` listens elsewhere and `--container NAME` names the container.

## Put TLS in front

`rookery serve` speaks plain HTTP, and an admin's sign-in gives full control of every host. Serve it behind a TLS proxy and use the `https://` address. Without one, keep the port on loopback or a private network such as your tailnet.

With Tailscale on the server:

```bash
sudo tailscale serve --bg --https=443 http://127.0.0.1:7777
```

Then set `ROOKERY_PUBLIC_URL=https://SERVER.TAILNET.ts.net` and restart the server, so the sign-in links and the session cookie name that address.

To open a host's ports in a browser outside `localhost`, set `ROOKERY_PORTS_URL` to a separate wildcard domain with TLS, such as `https://ports.rookery.example`. That keeps port cookies apart from the server ([`rookery serve`](/docs/extend/serve#ports-and-desktops-in-a-browser)).

## The first admin

`rookery server setup-key` asks the server, over its socket, for a one-time sign-in link. It prints the link, which signs in the first admin once, within a day. Whoever installs the server hands the link on and never sees a token.

```bash title="On the server"
docker compose exec rookery rookery server setup-key    # or: rookery server setup-key
```

Open the link in a browser. On your own machine, `rookery login` takes it as its address, or on standard input with `--link-stdin`:

```bash
rookery login https://rookery.example.ts.net/auth/link/CODE
```

An admin makes a link for another person with `auth.createLink`. `rookery server token --user NAME --admin` makes an access token for an account, and makes the account an admin when it does not exist.

## The key file and rekey

The key file holds the key that seals the secrets, the hosts' passwords and the key ring in the database. Back it up apart from the database: a backup of the database alone gives no secret away, and loses them all without the key.

To seal everything again under a new key, stop every server on the database and run:

```bash
rookery server secrets rekey --write-new-key /etc/rookery/secret.key.new
```

In a container, `docker compose run --rm rookery server secrets rekey --write-new-key /config/rookery/secret.key.new` writes the new key into the volume, and `ROOKERY_SECRET_KEY_FILE` then names it. It opens the values with the key of `ROOKERY_SECRET_KEY_FILE` and writes them sealed with the new one, in one transaction. `--new-key-file FILE` takes a key you made instead. Point `ROOKERY_SECRET_KEY_FILE` at the new file and start the server again.

## Bring in an older store

A Rookery before the server kept its state in a store of its own: a SQLite file, or a PostgreSQL database. `rookery server import` brings it into the server's database once, into an empty one:

```bash
rookery server import --from ~/.local/share/rookery/rookery.db \
  --key-file ~/.config/rookery/store.key --owner ada
```

The old store is only read. Stop the server first, and see [The database](/docs/use/store#from-an-older-store) for the options and what the import reports. In a container, put the old store in a folder the container mounts and run the import with `docker compose run --rm rookery server import ...`.

## Connect to it

`rookery login` signs in through the browser, keeps the server and the session, and every command after it uses that server:

```bash
rookery login https://rookery.example.ts.net    # opens the browser to sign in
rookery ls
rookery apply studio
rookery logout                                 # back to the rookery of this machine
```

`rookery login URL` opens `/auth/desktop` with a loopback redirect and a PKCE challenge, takes the code on the loopback address, and exchanges it for a device session. The session shows in `auth.listDevices`.

Without a browser, `--no-browser` asks for a sign-in link instead. With an access token in a file, `rookery login https://rookery.example.ts.net --token-file token` keeps it. For one command alone, give the server on its command line. That leaves the kept one alone:

```bash
rookery --server https://rookery.example.ts.net --token-file token ls
```

`ROOKERY_SERVER` and `ROOKERY_TOKEN` in the environment take precedence over what `rookery login` kept. A token never goes on the command line, where other users of the machine could read it.

### With a sign-in link

A sign-in link signs one person in once, without a password, and works for a day. The first admin's comes from `rookery server setup-key` ([The first admin](#the-first-admin)). An admin makes one for another person with `auth.createLink`, and `auth.revokeLink` ends one that was not used. Until a link is used it is as good as a sign-in, so keep it to yourself. Give it to `rookery login` on your own machine:

```bash
rookery login https://rookery.example.ts.net/auth/link/CODE
```

The address in it says what it reaches:

| Address | Reaches |
| --- | --- |
| `https://HOST[:PORT]` | A server behind a TLS proxy |
| `http://HOST:PORT` | A server's port directly |
| `unix:/path/to/server.sock` | A `rookery serve` on this machine, as its admin. Rookery finds the server's own socket by itself |

## Who may use it

An account that added a host owns it, and holds `manage` on `env://NAME`. `access.grant` gives another account or a group `view`, `use` or `manage` on the host, and `access.grants` says who holds what.

The levels are:

| Level | May |
| --- | --- |
| `view` | See the host, its state, jobs, output and a thumbnail of its desktop |
| `use` | Open terminals, sessions, files, ports, the desktop and agent sessions on it, and reach one's own `agent` terminals |
| `manage` | Change its profile, apply it, rename it, run its actions and its controller's, and reach any terminal |

`env.*`, `terminals.*`, `agents.connect`, forwarded ports and the desktop check these grants. Revoking a grant closes open streams on that host. Admins hold `manage` on every host, and what belongs to the installation, such as keys, secrets and plugins, needs an admin. [`rookery serve`](/docs/extend/serve#who-gets-in) has the methods, and an example of `access.grant`.

## Host agent sessions

A host that has the Parrot features runs an agent account's Parrot on its own socket, which the server reaches with `agents.connect`. The call needs `use` on `env://NAME`, and it ends when that level goes away, as a terminal's does.

The server stages the Parrot executable and the driver eggs of the agent packages the host's features select, and sends them with the apply. The host checks the runtime's checksum, each egg's checksum and the release name against what the server staged, and the host's architecture against the driver's, before it installs them. A package's driver is pinned when the plugin is installed, and an apply installs only that variant.

`ROOKERY_PARROT_BIN` on the server is the Parrot binary to send. Without it, an apply of a profile with agent features stops before it changes the host.

## On other systems

Rookery on macOS and Windows is the client of a server: `rookery login`, `rookery ls` and the other commands, which all call a server. Install it on Windows in PowerShell:

```powershell
irm https://raw.githubusercontent.com/aiviarium/rookery/main/install.ps1 | iex
```

On macOS:

```bash
curl -fsSL https://raw.githubusercontent.com/aiviarium/rookery/main/install.sh | sh
```

Each script downloads the latest release for this machine, checks it against its SHA-256 and installs it, to `%LOCALAPPDATA%\Programs\rookery` on Windows and to `~/.local/bin` on macOS. `ROOKERY_INSTALL_DIR` and `ROOKERY_VERSION` work as on Linux. To download it by hand, take the archive for your system and its `.sha256` file from the [latest release](https://github.com/aiviarium/rookery/releases/latest).

Then sign in, and see its hosts:

```bash
rookery login https://rookery.example.ts.net
rookery ls
```

Rookery keeps the server and its session or token as the settings `server` and `server_token`, in `config.json` of its folder of settings, which only you can read: `~/.config/rookery` on Linux, or under `$XDG_CONFIG_HOME`.

| Variable | Effect |
| --- | --- |
| `ROOKERY_SERVER` | The server, for this run |
| `ROOKERY_TOKEN` | The token, so it isn't asked for |

Rookery talks to a server over `https` only with a certificate that the system or the Mozilla roots trust. `rookery logout` forgets the server and its token.

A password the server makes up is shown once. The server keeps a copy in its database, and `rookery host credentials HOST` shows it again to an admin of the server.

What works with the server's own machine is offered there only. That is the USB installer, which writes a drive of that machine, and the settings that aren't open to the network. Elsewhere they are refused, with the reason.

## What works from another machine

Every command calls the server. Each works from another machine as it does on the server. These are the exceptions: they need the server's own machine, and say so elsewhere.

| Needs the server's machine | Why |
| --- | --- |
| Writing the USB installer to a drive | The drive is a device of that machine |
| `rookery registry publish` and `rookery registry push-image` | They upload files of that machine |
| `rookery server …` and `rookery serve` | They are the server itself |
| `rookery host inventory` | It reads Ansible's inventory on the machine it runs on |
| The settings that aren't open to the network | The server keeps them to its own users |

On macOS and Windows, `rookery host inventory` and the server's own commands are not built. Every other command works there as a client ([Not in this version](/docs/reference/not-in-this-version)).

### Setting the server up from here

As an admin of the server, Rookery sets the server up from anywhere. What you change is saved on the server:

- A host's set-up tabs, `rookery host create`, `rookery host set` and `rookery host import` save the profile there.
- A password the server generates is kept there. `rookery host credentials HOST` asks the server for it.
- `rookery apply HOST` and **Apply this configuration** run as a job on the server. Rookery follows its output as it comes ([Jobs](/docs/use/cli#jobs)).
- `rookery host seed HOST` has the server render the cloud-init seed, and writes it here.
- `rookery host create HOST --provisioner NAME`, `rookery host start` and `rookery host stop` use the server's provisioners and secrets ([Provisioners](/docs/deploy/provisioners#with-a-rookery-server)).
- `rookery resource` uses the server's resources. A deployment's specification is sent to the server and kept there, and it gets the server's secrets ([Deployments](/docs/deploy/deployments#with-a-rookery-server)).
- A secret's value is sent to the server and kept only there.
- The `tailnet_` settings and the secret `tailnet_api_key` are the server's, which creates the [keys its hosts join with](/docs/use/access#joining-the-tailnet) and looks after their [devices](/docs/use/access#the-hosts-device). Settings and `rookery config set` change them there.
- A plugin is installed on the server, and its features are offered for the server's hosts. An egg or package folder of yours is sent there first.
- The server logs in to hosts with the keys of [its own key ring](/docs/use/accounts#keys), by default its key `rookery`. `rookery key` acts on the server's ring, and its private halves stay there. `rookery key trust HOST` and `rookery host verify HOST --accept` make first contact and accept a changed host key from the server.
- `rookery key rotate` replaces a key on the hosts that take it, as a job of the server ([Rekeying](/docs/use/accounts#rekeying)).

Without `manage` on a host, the set-up says *This host is set up on the Rookery server at URL*, and the host's other commands work as before. Accounts, grants on hosts and access tokens are in [`rookery serve`](/docs/extend/serve#who-gets-in).
