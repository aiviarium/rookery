The Rookery server keeps its state in one PostgreSQL database: the hosts with their profiles and passwords, the key ring, secrets, settings, registries, jobs with their logs, accounts and grants. An installation can be restored on another machine from the database and its key file alone.

`ROOKERY_DATABASE_URL` names the database, and `rookery serve` migrates it when it starts. The [container image](/docs/extend/serve#in-a-container) runs a database of its own when it is not given one.

```bash
export ROOKERY_DATABASE_URL="postgres://rookery:PASSWORD@db.example.org/rookery?sslmode=require"
```

With `sslmode=require`, the server connects over TLS. A URL can contain the password, so give it in the environment or an environment file, never as an argument.

## The secret key

`ROOKERY_SECRET_KEY_FILE` names a file with the key that seals the secrets, passwords and the keys of the key ring in the database: 64 hex digits, or 32 bytes in base64. `ROOKERY_SECRET_KEY` gives the key itself. Without a key the server runs, and refuses everything that is sealed.

```bash
(umask 077; openssl rand -hex 32 > /etc/rookery/secret.key)
```

To seal everything again under a new key, stop every `rookery serve` on the database and run:

```bash
rookery server secrets rekey --write-new-key /etc/rookery/secret.key.new
```

It opens the values with the key of `ROOKERY_SECRET_KEY_FILE` and writes them sealed with the new one, in one transaction. Then point `ROOKERY_SECRET_KEY_FILE` at the new file and start the server.

<Callout type="warn" title="Back the key file up apart from the database">
  The sealed values cannot be read without the key. Keep a copy of the key file somewhere other than the backups of the database, so that one stolen backup doesn't give away the secrets. Keep the old key as long as you keep backups from before a rekey.
</Callout>

## What is in the database

| In the database | Kept as a file on the server's machine | Made again |
| --- | --- | --- |
| Host profiles, the passwords Rookery generated and the records of the machines it created | The secret key | The key files in `keys/` of the data directory, written from the database |
| Registries, secrets and settings, with the SSH and sudo passwords of hosts | Builds and installer ISOs | The known-hosts files in `known_hosts/` |
| The SSH keys of the key ring, and each host's host keys | | The plugin directory, from the database and the plugin registries |
| Jobs with their logs, the hosts' kept messages, notifications | | |
| Accounts, sessions, access tokens, groups and grants | | |
| Your own plugins, as `hatchery.kdl`, `eggs.lock` and the eggs that were sent | | |

ssh, Ansible and people read the keys as files. The server that leads writes them from the database before it opens links to the hosts, each key to `keys/NAME` of the data directory. A file that differs is moved aside to `keys/NAME.replaced`, and Rookery says so.

## Back it up and restore it

Back the database up with PostgreSQL's own tools, such as `pg_dump`, while the server runs:

```bash
pg_dump --no-owner "$ROOKERY_DATABASE_URL" > rookery.sql
```

To restore, load the dump into an empty database, put the key file in place and start `rookery serve` with both. The hosts, the jobs and their logs, the accounts and their tokens are there. The server writes its SSH keys back and logs in to the hosts with the same keys, and reinstalls your own plugins from their registries.

## From an older store

Rookery before the server kept its state in a store of its own: `rookery.db`, a SQLite file in the data directory, or a PostgreSQL database in the `store` setting. `rookery server import` brings it into the server's database once:

```bash
rookery server import --from ~/.local/share/rookery/rookery.db --key-file ~/.config/rookery/store.key --owner ada
```

| Option | Means |
| --- | --- |
| `--from` | The store's SQLite file, or a `postgres://` URL |
| `--key-file` | The old store's key file, when it was encrypted. Without it, the server's own key is tried |
| `--owner` | The account that owns every imported host. Without it, only admins see them |

- It writes everything in one transaction, and refuses a database that has hosts already.
- It never writes the old store.
- Secrets and passwords are sealed again with the server's key.
- The output of jobs within `retention_days` goes into the jobs' logs.
- It prints what it brought in, table by table, and what it skipped and why.

The server's old token is not carried over. Make an access token with `rookery server token --user NAME`. The container image runs the import by itself the first time it starts on volumes with an older store.
