This Rookery has one set of screens and one command line, both over a server's API. Many commands and names changed, and the store is converted the first time this Rookery opens it. Update in the order below, and make the backup first.

## The order

| Step | What | Why then |
| --- | --- | --- |
| 1 | Back up the store | Rookery 0.5 cannot read the store once this Rookery has converted it |
| 2 | Update the server | A client of this Rookery refuses a server of Rookery 0.5 |
| 3 | Update the clients | A client of Rookery 0.5 cannot work with the new server |
| 4 | Update the hosts' controllers | Rookery needs their actions, which the controller of Rookery 0.5 does not have |
| 5 | Make the server's machine a node, if it hosts Incus or Docker | Optional. It then gets `upgrade-server` for the next update |

### 1. Back up

For a server of the `rookery-server` recipe, stop it and copy its folder:

```bash
sudo docker stop rookery
sudo tar -C /srv -czf ~/rookery-0.5.tar.gz rookery
sudo docker start rookery
```

For a Rookery without a server, copy `~/.local/share/rookery` and `~/.config/rookery` while no Rookery runs. A store in PostgreSQL needs a dump, with the password in `~/.pgpass` rather than on the command line:

```bash
pg_dump --format=custom --file=rookery-0.5.dump --host=192.0.2.40 --username=rookery rookery
```

### 2. The server

Fetch the recipe of the new version and run it with `rookery_server_update`. It pulls the new image and makes the container again with the data and every option of the old one, such as the name `incus-host` and the Docker socket. The old container runs again if the new one does not come up:

```bash
curl -fsSL https://github.com/aiviarium/rookery/archive/refs/heads/main.tar.gz \
  | tar xz --strip-components=1 --wildcards '*/recipes' \
    '*/provision/ansible/roles/rookery/files/rookery-server-upgrade.py'
cd recipes/rookery-server
sudo ./install.sh -e rookery_server_update=true
```

Pass the options you gave the first run again, such as `-e rookery_server_node=true`. Do not remove the container by hand. A new container from the recipe gets the recipe's options alone. [Update it](https://github.com/aiviarium/rookery/blob/main/recipes/rookery-server/README.md#update-it) in the recipe's guide has the details.

For a server in a container you made yourself, run the same helper with the version to run:

```bash
sudo python3 provision/ansible/roles/rookery/files/rookery-server-upgrade.py rookery 0.6.0
```

A `rookery serve` that runs as a service is updated with `rookery update`, then restarted. Its command line may keep `--web`, which does nothing now.

### 3. The clients

```bash
rookery update
```

Install Rookery where rookery-remote was used: the [installation](/docs/start/install) replaces it. Rookery takes in the server and token rookery-remote kept, on the first command that needs a server:

| Rookery has | What happens to rookery-remote's settings |
| --- | --- |
| No server | Its server and token become Rookery's, and its file goes |
| The same server | Its token is taken when Rookery has none, and its file goes |
| Another server, or the same with another token | Its file stays. Rookery says so once, with `rookery login` for the other server |

A server that does not answer never costs Rookery the token it kept. Only `rookery logout`, signing out in the screens, or a new token in place of one the server refused replaces it.

### 4. The hosts

`rookery ls` marks each host whose controller is of Rookery 0.5 as `old controller`. Update them:

| Host type | Command |
| --- | --- |
| `workstation` or `node` | `rookery apply HOST` |
| `managed` | `rookery run HOST install-controller` |

Until then sessions, files and `rookery exec` work, and the host's actions and its page in the screens say that the controller is older.

### 5. The server's machine as a node

The `incus-host` recipe is gone. A machine it set up becomes a [node](/docs/use/nodes). Run the server recipe with `rookery_server_node`. Add the machine from a Rookery connected to that server, because the provisioners of the machine are that server's:

```bash
sudo ./install.sh -e rookery_server_node=true -e rookery_server_update=true
rookery host add big node --user root --type node \
  --feature docker/engine --feature incus/server
rookery apply big
```

The apply makes the recipe's Incus provisioners the node's. It says so for each, and names any it left alone. The provisioner of the server's local Docker engine is one of those, as Rookery cannot tell that it is the node's engine. Make it the node's by hand, and apply once more:

```bash
rookery provisioner run docker adopt node=big
rookery apply big
```

Use the name `rookery provisioner list` shows for it.

From then on, `rookery run big upgrade-server version=0.7.0` updates the server. `source=here` runs it from the Rookery you run instead, built on the node. [The Rookery server on a node](/docs/use/nodes#the-rookery-server-on-a-node) has the details.

## What is converted, and when

The first start of this Rookery on a store converts it, whether that is the server in its container or a command on your machine.

| What | Becomes |
| --- | --- |
| The schema of the SQLite file or the database | The schema of this Rookery |
| `level` and `profile` in every profile | `type` and `target` |
| `controller` as a type | `managed` |
| Keys pasted into profiles to join the tailnet | Removed. Rookery makes the keys with the secret `tailnet_api_key` |
| A host Rookery 0.5 never joined to the tailnet itself | Keeps applying without the tailnet until Rookery can make its key: its profile gets `rookery_tailnet_optional` |

The conversion happens once. A second start doesn't change the store.

## Going back

Before it converts a SQLite store, Rookery writes a copy of it beside the store, named for the version and schema it had, such as `rookery.db.rookery-0.5.2-schema-4`, and says where. Only the latest copy is kept. With no room for it, Rookery says so and converts the store without one.

Rookery 0.5 cannot read a converted store, and in a container it stops again and again. To go back, stop the new Rookery, put the copy in place and start Rookery 0.5:

```bash
sudo docker rm -f rookery
cd /srv/rookery/data/rookery
sudo mv rookery.db rookery.db.converted
sudo rm -f rookery.db-wal rookery.db-shm
sudo mv rookery.db.rookery-0.5.2-schema-4 rookery.db
```

Then run the recipe of Rookery 0.5 again, or `rookery serve` of that version. What changed after the upgrade is lost. A store in PostgreSQL goes back from the dump of step 1 with `pg_restore`. Rookery doesn't copy it, and prints a line when it converts one.

## Names

| Before | Now |
| --- | --- |
| A host's `level` | Its `type` |
| The level `controller` | The type `managed` |
| A profile's `profile`, such as `laptop` | Its `target` |
| Tasks of a host | Its actions: `rookery run HOST ACTION` |
| `rookery connect URL` | `rookery login URL` |
| rookery-remote | Rookery: `rookery ui` opens the screens |
| The page in the browser | The screens and the command line. The server's address shows a line about `rookery login` |
| The `incus-host` recipe | A node with the features `incus/server` and `docker/engine` |
| `tailscale_auth_key` and `tailscale_auto_key` in a profile | The secret `tailnet_api_key`, from which Rookery makes each host's key |

## API clients

The API is number 2 now, and `GET /v1/version` says so in `api`. A client of Rookery's own refuses a server with an older number. A call that only Rookery 0.5 makes gets an error that names Rookery 0.5.

| Before | Now |
| --- | --- |
| `level` in hosts and profiles | `type` |
| `profile` in a profile | `target` |
| `/v1/tasks`, `tasks.list`, `tasks.run` | `/v1/actions`, `actions.list`, `actions.run` |
| The server's `actions.act` | `hosts.act`, `installation.act`, `provisioners.act` and `resources.act` |

The [API reference](/docs/api/serve) lists every operation.
