Two programs have an API. rookeryd runs on every host, and `rookery serve` is the server that keeps the hosts.

| Program | Runs on | Reached at | Reference |
| --- | --- | --- | --- |
| rookeryd | every host, as root | unix sockets in `/run/rookery` | [rookeryd](/docs/api/host) |
| `rookery serve` | a server, with its PostgreSQL database | `/ws` and `/rpc` over TCP, and a unix socket on its machine | [`rookery serve`](/docs/api/server) |

The server reaches each host's rookeryd itself. A client of the server never talks to rookeryd: what it does on a host is a method of the server, such as `hosts.sessions.open` or `hosts.files.read`, with the host in its parameters.

## The server's methods

Every method of the server has a name, such as `hosts.list` or `jobs.follow`, and takes its parameters as one JSON object. It is called as JSON-RPC 2.0:

| Way | For |
| --- | --- |
| `GET /ws` | A WebSocket for many calls and streams at once. Crow and the `rookery` command line use it |
| `POST /rpc` | One call per request, for scripts. Methods that open a stream are refused there |
| The unix socket | `/ws` and `/rpc` on the server's own machine, `server.sock` in Rookery's runtime folder or `ROOKERY_SOCKET`. Its caller is the machine's admin |

```bash
curl -H "Authorization: Bearer $ROOKERY_TOKEN" -d '{"jsonrpc": "2.0", "id": 1, "method": "hosts.list"}' \
  https://rookery.example.ts.net/rpc
```

```json
{ "jsonrpc": "2.0", "id": 1, "result": { "hosts": [{ "name": "studio", "reachable": true }] } }
```

On `/ws` a browser signs in with its session cookie, and any other client sends a bearer token in `Authorization`. `rookery server token --user NAME` makes an access token on the server's machine.

## Streams

A method that opens a stream, such as `jobs.follow` or `hosts.sessions.attach`, answers with `{"stream": ID}`. The stream's data then comes as binary WebSocket frames: 4 bytes of the stream's id, big endian, then up to 64 KB of payload. The same frames go the other way for a stream that takes input, such as a terminal or `hosts.ports.connect`.

Each direction starts with 256 KB of credit. A reader grants more with `streams.credit` as it takes data, and a writer waits while it has none, so a slow reader never fills the server. `streams.eof` ends one direction and `streams.close` both. A peer that sends more than its credit loses the stream.

## Errors

An error is JSON-RPC's, with Rookery's code in `data`:

```json
{ "jsonrpc": "2.0", "id": 1, "error": { "code": -32002, "message": "no host forge", "data": { "code": "NOT_FOUND" } } }
```

| `data.code` | Means |
| --- | --- |
| `INVALID` | The parameters fail the method's schema, or the request is wrong |
| `UNAUTHENTICATED` | No session or token that works: sign in again |
| `FORBIDDEN` | The caller lacks the level the method needs |
| `NOT_FOUND` | No such method, host, job or thing |
| `CONFLICT` | A revision did not match, or something else holds what this changes |
| `UNAVAILABLE` | Something it needs is not there, such as a host that does not answer. A host's refusal is in `data.details` |
| `TIMEOUT` | The call's deadline passed |
| `INTERNAL` | Something failed inside. A job's command that failed says its exit code in `data.details.exit` |

## Who may call

Each method says who may call it: anyone, any signed-in caller for itself, an admin, or a caller that holds `view`, `use` or `manage` on the resource the method is about. A host is the resource `env://NAME`, and `access.grant` gives another account a host. See [Who gets in](/docs/extend/serve#who-gets-in).

rookeryd answers on two sockets, and each of its operations says which may use it:

| Socket | Level | Who connects |
| --- | --- | --- |
| `/run/rookery/control.sock` | host | root. Rookery reaches it over SSH with `sudo -n rookeryd connect` |
| `/run/rookery/agent.sock` | agent | the agent account; `box` uses it |

In a container rookeryd runs for the agent alone, without systemd, and calls that need systemd or another user are refused.

## rookeryd's operations

Each operation of rookeryd can be called in two ways:

| Way | For |
| --- | --- |
| [The portal](/docs/api/portal) | One WebSocket at `/v1/portal` for many calls and streams at once |
| HTTP | One request per call, at the operation's path. Simple to try with `curl`, and the way to move more than 8 MB |

`version` answers with `api`, a number that rises when something is added to rookeryd's API. The server compares it to see what a host can do, and `hosts.list` gives each host's number.

Over HTTP an error of rookeryd is a status code with a JSON body; on the portal the same object comes back under the request's `id`:

```json
{ "error": { "code": "not_found", "message": "No session k3v9qz2m8w1x", "status": 404 } }
```

## The documents

The reference is generated from documents that the programs print and the tests keep current. Use them for tooling:

| Document | Printed by | Download |
| --- | --- | --- |
| Operations of rookeryd | `rookeryd operations` | [rookeryd.operations.json](/openapi/rookeryd.operations.json) |
| OpenAPI 3 of rookeryd | `rookeryd openapi` | [rookeryd.openapi.json](/openapi/rookeryd.openapi.json) |
| AsyncAPI 3 of rookeryd | `rookeryd asyncapi` | [rookeryd.asyncapi.json](/openapi/rookeryd.asyncapi.json) |
| Methods of `rookery serve` | the test `the_method_report_is_current` of rookery-server | `api/methods.json` in the repository |

The methods document lists each method with its summary, who may call it, whether it opens a stream, and the JSON schemas of its parameters and result. The TypeScript types of the same are in `@rookery/client`.
